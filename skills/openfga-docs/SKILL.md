# OpenFGA Documentation

Use this skill for changes in `openfga/openfga.dev`. The repository is a Docusaurus 3 site with React, TypeScript, JavaScript, and MDX. Confirm current dependency versions and scripts in `package.json` before relying on them.

## Non-negotiable boundaries

- Author product documentation in `docs/content/**/*.mdx`.
- Maintain docs ordering and grouping in `docs/sidebars.js`; maintain global navigation, redirects, and plugin behavior in `docusaurus.config.js`.
- Reuse documentation components from `src/components/Docs/` and Docusaurus theme components before inventing new MDX patterns.
- Do not hand-edit `docs/content/getting-started/setup-openfga/configuration.mdx`. It is generated by `scripts/update-config-page.mjs` from the latest released OpenFGA `.config-schema.json`.
- Do not hand-edit `build/llms.txt`, `build/docs/llms.txt`, `build/llms-full.txt`, or adjacent `build/docs/**/*.md` pages. They are build output.
- Treat the OpenAPI document configured by `customFields.apiDocsBasePath` as authoritative for HTTP request and response shapes.
- Keep changes focused. Do not copy large sections of upstream product or API documentation into the site.

Read [repository-map.md](references/repository-map.md) before changing structure or generation behavior.

## Choose the page intent

Use Diataxis as a decision aid, not as a forced directory rewrite:

- **Tutorial:** lead a learner through a successful first outcome.
- **How-to:** solve a concrete task for a reader who already has context.
- **Reference:** state exact syntax, fields, defaults, or contracts without narrative detours.
- **Explanation:** clarify concepts, tradeoffs, or design reasoning.

Keep one dominant intent per page. Read the nearest sibling pages and [content-authoring.md](references/content-authoring.md) before drafting.

## Workflow

1. **Inspect the live repository.**
   Read `package.json`, `docusaurus.config.js`, `docs/sidebars.js`, the target page, nearby pages, and any imported component. Check the current OpenFGA or API source when documenting product behavior.

2. **Identify the source of truth.**
   Decide whether the change belongs in authored MDX, navigation, a React component, the configuration generator, the agent-content pipeline, or the upstream OpenAPI/config schema. Never patch generated output to conceal a source problem.

3. **Draft for the reader's task.**
   Give the page a specific `title` and `description`, state prerequisites, use descriptive headings, and put the expected outcome near the relevant step. Preserve local MDX and component conventions.

4. **Use correct OpenFGA language and executable examples.**
   Keep authorization model, type, relation, relationship tuple, user, object, store, userset, condition, and authorization model ID distinct. Use schema `1.1`, valid tuple syntax, and current API/CLI commands. Read [openfga-examples.md](references/openfga-examples.md).

5. **Wire discovery surfaces.**
   Add or move sidebar entries deliberately. Preserve old public routes with redirects when renaming. Verify headings, anchors, related links, and Swagger deep links. Read [links-navigation-api.md](references/links-navigation-api.md).

6. **Protect human and agent readers.**
   Make MDX semantic without JavaScript, ensure custom UI is keyboard accessible and responsive, and ensure important information survives conversion to adjacent Markdown. Read [accessibility-responsive.md](references/accessibility-responsive.md) and [generated-agent-docs.md](references/generated-agent-docs.md).

7. **Validate the complete output.**
   From a clean dependency install, run the existing checks:

   ```bash
   npm ci
   npm run format:check
   npm run lint
   npm run typecheck
   npm run build
   ```

   `npm run build` generates the configuration page, builds Docusaurus, prepares agent-readable content, and validates that content. Review the working tree afterward so generated release drift is not mixed into an unrelated change. Follow [validation-preview.md](references/validation-preview.md) for link checks and previews.

## Completion criteria

- The page has one clear reader intent and uses current OpenFGA terminology.
- Examples are internally consistent and runnable with their stated prerequisites.
- Source-of-truth and generated-file boundaries are respected.
- Navigation, redirects, links, anchors, API references, and agent-readable output remain coherent.
- Changed UI works with keyboard navigation and narrow and wide viewports.
- `format:check`, `lint`, `typecheck`, and `build` pass, with link-check expectations reviewed.
